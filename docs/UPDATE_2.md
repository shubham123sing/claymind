## Step 1: PLAY KIT (no AI, fully offline)
**Idea:** a Play Kit is the user's own toy box: things they made (clay board, clay balls, clay ramp, clay cups) plus a **Set** (a saved arrangement on the table) they can play with, using physics and rules.
- **Add to Play Kit** (separate from Library; one creation can be in both). Each kit item stores: id, name, creation data (same format as Library/.claymind.json), thumbnail, **role tag** (board, piece, launcher, target, obstacle, container, other; editable), measured stats (size, mass, material, count of parts).
- **Play Kit list** screen: grid/list of items with Rename, Change role, Duplicate, Remove from kit, Undo toast. Big hand-friendly cards, pinch to pick, hide/show like the rest of the menu.
- **Sets:** the user places kit items on the table, names the arrangement, and saves it as a Set (positions, scale, pinned, physics settings). Open / rename / delete Sets. Export/import `.claymind.json` includes the kit.
- **Edit / Play toggle:** Edit mode = place and adjust; Play mode = physics runs, hands can flick, throw, push, drop; a Reset button returns the Set to its start state (exact); pause/resume works.
- **Rule engine (code, no AI):** a small **Game Spec** (JSON, schema-validated, versioned) that a deterministic interpreter runs. A Game Spec lists: roles needed, win/score conditions, turn rules, allowed hand actions, and a scoreboard. Triggers are a fixed list: `enters_zone`, `leaves_zone`, `falls_below_height`, `comes_to_rest`, `hit_by`, `stack_height_reached`, `timer`, `count_reached`. Actions are a fixed list: `add_score`, `end_turn`, `respawn`, `reset_piece`, `show_message`, `win`, `lose`. **No arbitrary code is ever executed from a spec.**
- **Built-in game templates (build 5, polished, each with a clear how-to-play card):** (1) Knock-down (stack of clay blocks, throw balls, count fallen), (2) Flick-and-pocket (board with rim and holes, flick pieces, score pockets; carrom-like), (3) Target throw (rings/balls into cups or zones), (4) Tower balance (stack height, topple = end), (5) Marble run (ramp, marbles, finish zone, timer). The user picks a template, maps their kit items to the roles (auto-suggested by role tags and measured sizes), and plays.
- Accept: with the network off, a user adds 3 creations to the kit, saves a Set, plays Knock-down and Flick-and-pocket with hands in the emulator, resets, and exports/imports the kit.

## Step 2: agent backend (Agno), optional layer
Python backend (FastAPI + Agno `AgentOS`), same provider chain and Quota Governor idea as Story Theatre (free LLMs, strict-JSON schemas, caching by input hash, timeouts ~12 s, degrade, never freeze). Read the installed Agno docs first, pin the version. Run all agents in one process; the Helper reaches Researcher, Designer and Coach through **A2A calls** on local URLs, with an in-process fallback switch (`A2A_MODE=local|inproc`); shared-token auth on A2A routes. Keys only in server env, never in the client or git. Backend and client both HTTPS, CORS locked to the app origin, rate limit per IP.
Agents (narrow jobs, one `Agent.run(input) -> PydanticModel` interface):
| Agent | Job |
|---|---|
| **Helper** (home agent) | talks to the user, routes requests: "teach me to build X", "what can I do with my kit?", "make a game from my kit", "I'm stuck" |
| **Kit Analyst** (mostly code) | turns each kit item into a **shape descriptor** from geometry, not from pictures: bounding box, flatness, wall height/rim, cavity, hole count, roundness, symmetry, mass, material, plus the user's name and role tag; suggests roles |
| **Researcher** | when the user names a game/object the app does not know, searches the web, reads a few pages, and writes a **Rule Card** (goal, pieces, setup, turns, scoring, common variants, sizes), in its OWN words with source URLs; cached |
| **Game Designer** | maps a Rule Card + the user's kit onto the Game Spec DSL (choose template or compose from the trigger/action lists), proposes size/mass adjustments, and says what is missing ("you need 8 pieces and a rim") |
| **Referee** (code) | validates the spec (schema, every role mapped, win reachable, no impossible triggers) and dry-runs it in headless physics for N seconds before it is offered; repair loop max 2, else a safe built-in template |
| **Coach** | step-by-step build guide for a thing the user wants to make; checks the user's creation against the guide's measurements and gives a specific fix ("rim is 1 cm, balls are 2 cm, raise by 1.5 cm"); never judges taste |
- **Knowledge for the Helper:** a small per-user **Kit KG** (nodes: Item, Role, Game, Rule, Source, Set; edges: `can_be`, `needs`, `fits`, `variant_of`, `cites`) plus a passage index of cached Rule Cards and researched pages (**RAG + GraphRAG**: local queries hop from the user's items to games they could play; global queries summarise what the kit supports). **Memory:** the user's kit and sets, games played, rules they changed, preferences; "Delete my data" erases it. Embeddings with a small open model, local vector store, no paid services.
- **When the web is used (rule of priority):** (1) the user's own rules ALWAYS win and need no web; (2) a built-in template or cached Rule Card is used next; (3) the Researcher/web runs ONLY when the user says they don't know the rules ("I don't know how to play", "teach me", "surprise me with a real game") or names a game that is unknown and gave no rules. If the user gave partial rules, keep theirs and use the web only to fill what is missing, marking which parts came from the web. Never search just because it is possible; the web is off by default for a request and the app says "using your rules" or "looking up the rules" so the user knows which path ran.
- **Web search:** use one search source with a free tier that you verify is currently available (and Wikipedia's API as a no-key baseline); record the choice in docs. Fetched web text is **untrusted data**: strip scripts, never follow instructions in it, summarise in own words, keep short quotes only, always show sources, respect copyright. If search fails, answer from cached Rule Cards or say "I couldn't find the rules" and offer the closest built-in template.
- Safety: block unsafe/violent/adult requests with a friendly "that doesn't fit here"; the user's text is untrusted input to every prompt.
- Trace: log each agent call (agent, model, tokens, ms, cached) to a ring buffer; optional "Agent activity" panel (off by default, on for the demo).

## Step 3: agent features in the app
- **Make a game from my kit:** user taps "Make a game", picks a game name from cards or types one on the 2D page / pinch keypad ("carrom", "bowling", "I don't know, surprise me"). Flow: Kit Analyst -> Researcher (if unknown) -> Designer -> Referee -> **preview card** (name, how to play in 4 lines, what it uses from your kit, what is missing) -> Play / Adjust / Cancel. "Surprise me" picks the best fit from the kit's descriptors. **Custom rules in the user's own words** (typed on the 2D page or built from cards/pinch keypad; no voice): e.g. "whoever knocks down 5 blocks first wins", "3 turns each, bigger pocket scores more". The Designer turns them into a Game Spec using only the fixed trigger/action lists; whatever cannot be expressed is said plainly ("I can't do X, closest is Y") and offered as an alternative, never silently dropped. The user can edit the generated rules on a simple rules card (score values, number of turns, time limit, win count) and re-run the Referee. The Set is created automatically with correct positions and scale.
- **Teach me to build X:** Coach produces 5-10 steps mapped to ClayMind tools (shape, size in cm, material, colour). Show one step at a time on a small panel; "Check my work" measures the current creation against the step and responds with a specific fix or "looks good". Optional stretch: a translucent **ghost outline** on the table for the target shape.
- **Stuck / mistake help:** "Help" opens the Helper with the current context (what is selected, last action); it explains in 1-3 sentences and offers one button that does the fix when it is safe (always undoable).
- Every agent answer shows sources when it used the web, and says plainly when it guessed.
- If the backend is off: the Helper says "AI helper is offline, built-in games still work" and the built-in templates, kit and sets keep working.

## Step 3b: SIMULATE it for me (the Helper shows, the user watches)
The user can say "simulate this" on any creation, Set or game, and the Helper runs it and shows the result.
- **Demo play ("Show me how to play"):** after a game is made, a **demo player** performs a few turns on the real table with the real physics: a translucent **ghost hand** flicks/throws/pushes using only the actions a human hand can do (impulse strength and speed within a human range, from the same action list as the Game Spec), so what it shows is achievable. The scoreboard updates live; the user can pause, replay, slow down, and say "my turn" to take over from the exact state.
- **Test my creation ("Will it work?"):** headless physics runs on the user's creation: will the tower stand, does the ball roll off the ramp, does the board hold pieces, does the marble reach the finish. Show the result as a short visible run plus 1-3 plain sentences and one suggested fix ("add a wider base, +2 cm") with a button that applies it (undoable).
- **What-if sim:** the user picks a change ("heavier ball", "higher rim", "steeper ramp") or asks for one; the Helper runs 5-10 quick headless variants with a fixed seed, shows the best one, and offers to apply it. Variants are limited to size, mass, material, angle and position within safe ranges.
- **Rules:** the simulation uses the same engine and Game Spec as normal play (deterministic with a seed, so a replay is identical); no arbitrary code; run time capped (for example 20 s visible, 60 s headless) with a Stop button; heavy headless runs may use a Web Worker or the backend but must degrade to a shorter run offline; the demo player and Test work with NO AI using the built-in templates (the AI only decides what to demo or which fix to propose).
- **Honesty for the video:** anything the demo player or a simulation does is labelled "Demo" on screen in the app and must not be shown in the submission video as the user's own hand use; the video must show real hand interaction (emulator footage is allowed but must honestly represent real use).
- Accept: with the network off, "Show me how to play" runs a full Knock-down and Flick-and-pocket demo, "Will it work?" gives a correct pass/fail on a stable and an unstable tower, and a What-if sim returns a better variant with the same result on replay.
